# 核心启动管线

> 这是内核（L0）的设计。内核代码评审的唯一否决标准：**这行代码是否只服务于"启动一个 Minecraft 实例"的最小闭包。**

---

## 1. 目录布局

```
<数据根>/                       # 用户可选，默认 %APPDATA%/ML 或 ~/.local/share/ml
├── config/
│   ├── global.json             # 下载源、语言、主题、全局内存、并发数
│   └── accounts.json           # 账户元数据（token 单独加密存 credential store）
├── shared/                     # 共享区（未启用版本隔离时全局共用）
│   ├── libraries/
│   ├── assets/
│   │   ├── indexes/
│   │   └── objects/
│   └── versions/
├── instances/
│   └── <实例id>/
│       ├── instance.json       # 实例元数据（名称、MC 版本、加载器、Java 路径、内存…）
│       ├── .minecraft/         # 实例的游戏目录（可被"打开文件夹"指向）
│       │   ├── mods/  config/  saves/  resourcepacks/  logs/  crash-reports/
│       │   └── versions/<vid>/<vid>.json + <vid>.jar
│       └── natives/            # 运行时解压的 natives（每次启动重建）
├── runtime/
│   └── java/<vendor>-<major>-<arch>/   # 下载的 JRE
├── plugins/                    # 见 01
├── state/
│   ├── installed.json          # 已安装插件
│   ├── plugin-health.json      # 熔断计数
│   └── last-session.json       # 非正常退出检测
└── logs/
    ├── ml.log
    ├── plugin-audit.log
    └── launch-<instance>-<ts>.log
```

**版本隔离**（PCL/HMCL 都有这个概念）的实现方式：隔离开 = `instance.json` 指向 `<实例>/.minecraft`，且该实例用私有 `versions/`、`mods/`；隔离关 = 指向 `shared/`。建议默认**开启隔离**（新手最常踩的坑就是"不同版本模组互相污染"）。

**要不要兼容读取已有 `.minecraft`？** 要。提供"导入现有游戏目录"：探测 `.minecraft/versions/*/` 与 `launcher_profiles.json`，为每个版本生成一个实例条目，不移动任何文件。这是降低用户迁移成本的关键，工作量很小。

## 2. 版本元数据解析

### 2.1 继承链

每个版本有一个 `<vid>.json`。加载器（Forge/Fabric）的版本文件通过 `inheritsFrom` 指向原版：

```json
{
  "id": "1.20.4-forge-49.0.30",
  "inheritsFrom": "1.20.4",
  "libraries": [ ... ],
  "arguments": { "game": ["--launchTarget", "forgeclient"], "jvm": [] },
  "mainClass": "cpw.mods.bootstraplauncher.BootstrapLauncher"
}
```

解析流程：

```
resolveVersion(vid):
    json = read(versions/vid/<vid>.json)
    if json.inheritsFrom is null:
        return json
    parent = resolveVersion(json.inheritsFrom)     // 递归，需检测环
    return merge(parent, json)                     // 子覆盖父
```

`merge` 的规则必须逐字段定义，不能"深拷贝覆盖"了事：

| 字段 | 合并方式 |
|---|---|
| `libraries` | **按 `group:artifact` 键合并**，子版本同名库覆盖父版本（这是 Forge 替换 LWJGL/ASM 版本的方式）；保留顺序：父在前，子新增的在父之前插入（Forge 依赖自身优先） |
| `mainClass` | 子覆盖父 |
| `assets` / `assetIndex` | 子覆盖父 |
| `arguments.game` | **拼接**：子在前，父在后？（实际是父在前、子在后，且 Forge 用 `--launchTarget` 追加）→ 结论：**父在前子在后拼接**，与官方启动器一致 |
| `arguments.jvm` | 父在前子在后拼接 |
| `minecraftArguments`（旧格式） | 若存在则转换为 `arguments.game`（按空格分割，注意引号） |
| `javaVersion` | 子覆盖父，父缺失时用子 |
| `downloads` | 子覆盖父 |
| `logging` | 子覆盖父 |

这里有个真实陷阱：**`libraries` 合并的键**。官方规范里同 `name` 不同 `classifiers` 是两个条目（如 `org.lwjgl:lwjgl:3.3.1` 和 `org.lwjgl:lwjgl:3.3.1:natives-windows`）。键必须用 `group:artifact:classifier`（不含 version），这样"只换版本"才能正确覆盖。

### 2.2 rules 求值

`libraries[].rules` 与旧版的 `libraries[].natives` 决定某个库是否在当前平台生效：

```json
{
  "name": "org.lwjgl:lwjgl:3.3.1:natives-windows",
  "rules": [{ "action": "allow", "os": { "name": "windows" } }]
}
```

求值算法（这是官方行为，必须精确）：

```
allowed = false                                  // 无 rules 时默认 true，有 rules 时默认 false
for rule in rules:
    if rule 的所有条件都满足（os.name / os.arch / os.version 正则 / features）:
        allowed = (rule.action == "allow")
    // 注意：不满足条件的 rule 直接跳过，不产生任何效果
```

`features` 是启动器自己可开关的开关位（如 `is_demo_user`、`has_custom_resolution`、`has_quick_plays_support`），默认全 false。**这一点决定了一个 UI 功能**：是否允许自定义分辨率 → 决定 `--width/--height` 是否传。

平台匹配细节：
- `os.name`：`windows` / `osx` / `linux`。macOS 判定要看 `Environment.OSVersion.Platform`，**不要**用 `RuntimeInformation.IsOSPlatform(OSPlatform.Windows)` 之外的字符串匹配。
- `os.arch`：值有 `x86` / `x64` / `arm64`。注意 ARM64 的 Mac 上 `x64` 与 `arm64` 都要能匹配（Rosetta / 原生）。
- `os.version` 是**正则**，不是版本比较。

## 3. 下载引擎

> **位置变更（2026-10-21）**：下载**已整体移出内核**，现在的家是 `src/ML.Features/Download/`，
> 将来搬进第一个官方插件 `ML.Plugin.Installer`。内核的边界是「从磁盘上已有的东西启动一个实例」，
> 零网络；`tests/ML.Core.Tests/ArchitectureTests.cs` 用程序集引用做断言，把这条边界钉死。
>
> 下面三节内容仍然有效（它是功能层的实现说明与设计依据），只是**不再属于 `ML.Core`**。
> 保留原文的理由：这些坑与取舍是拿真机流量换来的，删掉就要重踩一次。

### 3.1 核心要求

| 要求 | 做法 |
|---|---|
| 多源 | `IDownloadSource` 链（插件可扩展），按优先级依次改写 URL；主机级黑白名单 |
| 并发 | 全局限流（默认 8）按主机分桶（避免单站被打挂）；用 `SemaphoreSlim` 而非 `Parallel.ForEach` |
| 校验 | SHA1（MC 官方给的）为主，SHA256 可作为插件附加校验；**校验失败必须删除并重试**，不能保留坏文件 |
| 断点续传 | `Range` 请求 + 已有文件大小作为 offset；服务器不支持 Range 时（`Accept-Ranges: none`）整文件重下 |
| 原子性 | 下载到 `<target>.part`，校验通过后 `File.Move(overwrite: true)`；中断只会留下 `.part` |
| 幂等 | 已存在且哈希正确 → 直接跳过（这是二次启动快的原因，必须做） |
| 可取消 | 全链路 `CancellationToken`；取消时保留 `.part` 供续传 |

### 3.2 下载队列模型

```
DownloadPlan
  ├── items: List<DownloadItem> { Uri, TargetPath, Sha1?, Size?, Kind, SourceCandidates }
  └── ExecuteAsync(context):
        phase 1  校验本地（并发读文件算 SHA1，CPU 密集→限并发到 CPU/2）
        phase 2  缺失项按 Kind 分组（libraries/assets/java/installer），分别限流
        phase 3  失败聚合：单 item 重试 3 次（指数退避 1s/2s/4s），全失败则整批失败并报告
```

进度上报：以**字节**为权重而不是条目数（一个 8MB 的 jar 和一个 200B 的 json 权重不该相同）。UI 显示"总进度 + 当前 N 个任务 + 速率"。

### 3.3 镜像源

内置两个源：**Piston 官方**（`piston-meta.mojang.com`、`launchermeta.mojang.com`、`resources.download.minecraft.net`、`libraries.minecraft.net`）与 **BMCLAPI**（`bmclapi2.bangbang93.com`），后者对中国大陆用户意义重大。

要点：
- 镜像改写只针对**库/资源/清单**，**不代理微软登录**（那必须直连官方）。
- 镜像可能缺失新版本文件 → 失败后**自动降级到官方源**，不能硬失败。
- 用户可配置"镜像优先 / 官方优先 / 仅官方"。

**接缝落在哪（m01251 已实现一半）**：内核必须提供"从哪拿字节"的可替换点，但"管哪些镜像、什么时候切"是插件的事。

| 接缝 | 现状 |
|---|---|
| 资源对象 CDN | 已可替换：`AssetInstaller.BuildDownloads(paths, index, resourceBaseUrl)` / `ObjectUrl(hash, resourceBaseUrl)` / `new GameInstaller(paths, queue, resourceBaseUrl)`，留空 = 官方 |
| 库与清单 URL | **未做**。库 URL 现在直接取 `version.json` 里的 `downloads.artifact.url`，要替换得在生成下载任务时改写 host |
| 失败自动降级 | **未做**。目前一条 URL 失败重试 3 次就记失败，不会换源 |

一个语义坑（已修）：`DownloadReport.TotalBytes` 现在只累计**真正走过网络**的字节。早先它把"已存在、跳过"的文件大小也算进去，导致第二次启动时界面显示"已下载 621 MB"——用户看到的是"全都跳过了却还在下载"。这类数字必须区分**传输量**与**占用空间**，混用会让人以为校验没生效。

## 4. natives 与 assets

### 4.1 natives 解压

新版（1.19+）把 natives 直接作为普通库（`natives-windows` classifier）提供，旧版用 `natives` 字段指定 zip 内的子项名。

流程：
1. 收集所有 classifier 含 `natives-<os>` 的库 → 得到 jar 列表。**但光看 `rules` 会错**，见下面的陷阱。
2. 解压到 `versions/<id>/natives/`，**排除** `META-INF/`（不排除会引发签名冲突和 ServiceLoader 混淆）。
3. 旧格式：`natives` 字段是 `{"windows": "natives-windows-${arch}"}` 这种**模板**，要替换 `arch`（`32`/`64`）后作为 classifier 找库。
4. 幂等靠 `versions/<id>/natives/.ml-natives.json` 清单（jar 路径→sha1 + 已解压文件列表）；jar 集合一变就清空重解，文件被删掉就重解。

#### 必须做架构过滤（真机实测的坑）

1.20.1 里每条 LWJGL 库都有三个 Windows 变体，而它们的 `rules` **只判断 `os.name == windows`，完全不管架构**：

```json
{"name": "org.lwjgl:lwjgl:3.3.1:natives-windows-arm64", "rules": [{"action":"allow","os":{"name":"windows"}}]}
```

所以在 64 位 Windows 上，规则层面放行 `7 × 3 = 21` 个 jar，其中只有 7 个是对的。**照 rules 无脑解压，`lwjgl.dll` 会被 x86 或 arm64 版本覆盖**，游戏拿到错位数的 dll，表现为 `UnsatisfiedLinkError` 或进程直接退出。

`rules` 帮不上这个忙，只能自己按分类器后缀判断架构（`natives-windows` = 64 位，`-x86` = 32 位，`-arm64` = arm64）。这是 `Install/NativeClassifier.cs` 存在的唯一理由，也是这段代码里最容易写错的一行。

实测：`ml-verify natives` 在 1.20.1 上选中 7 个、按架构跳过 14 个，解压 39 ms 得到 18 个文件。数字见 `docs/性能基线.md` 第 7 节。

> 待定：natives jar 是否也要进 classpath。当前只解压、靠 `-Djava.library.path` 提供（与 Mojang 的启动器一致）；这条要在启动参数阶段连同 classpath 一起定，先记在这里，不预设结论。


### 4.2 assets

> **位置**：assets 的索引解析、`assets/objects/ab/…` 路径计算、旧版 `virtual` / `map_to_resources` 摊平，
> 现在都在 `src/ML.Features/Assets/`。原因是启动一个实例**不需要读索引**——游戏自己按哈希去
> `assets/objects/` 里取；只有"装"才需要索引。这条正好说明内核边界不是按"技术难度"切的，
> 而是按"少它起不来"切的。

```json
{ "objects": { "icons/icon_16x16.png": { "hash": "ab12...", "size": 1234 } } }
```

存储路径：`assets/objects/<hash[0..2]>/<hash>`（前两位做目录，这是官方布局，别自创）。

两种映射模式：
- **`virtual`**（旧版 resources）：需要把 objects 复制/硬链接成 `assets/virtual/<virtualName>/<原路径>`，游戏按原路径读。
- **`map_to_resources`**（更旧）：复制到实例的 `resources/` 目录。

> 当前实现（`Assets/AssetInstaller.MaterializeLegacy`）是**复制**，够用且最简单。Windows 上可换硬链接（`CreateHardLink`）省掉数 GB 磁盘，跨卷时仍回退复制——这是明确的待优化项，不是遗漏。

## 5. 模组加载器安装

### 5.1 Fabric / Quilt（简单）

从 Meta API 拿 loader 版本与 profile JSON，直接生成本地版本 json：

```
GET https://meta.fabricmc.net/v2/versions/loader/<mcver>
GET https://meta.fabricmc.net/v2/versions/loader/<mcver>/<loaderver>/profile/json
```

profile JSON 已是完整可用的 `inheritsFrom` 版本文件 → 写入 `versions/fabric-loader-<lv>-<mcver>/`，把 `libraries` 里的 URL 喂给下载引擎。**不需要跑 Java。**

### 5.2 NeoForge（中等）

Maven 上有 `net.neoforged:neoforge:<ver>:installer`，与 Forge 同构（走 5.3 流程），但 API 与 maven 坐标不同。

### 5.3 Forge（困难，必须单独模块）

Forge installer jar 里有两样东西：
- `install_profile.json`（新版在 `versionInfo` 里内嵌完整版本 json）
- `data/client.lzma`（processor 用的数据表）+ `maven/` 内嵌依赖

流程：

```
1. 下载 installer jar（library 坐标 net.minecraftforge:forge:<mc>-<forge>:installer）
2. 解压到临时目录
3. 读 install_profile.json
   ├── 若有 versionInfo → 直接写出 versions/<vid>/<vid>.json（继承原版）
   └── 若只有 version（旧版）→ 拼装
4. 解析 processors[]：
   {
     "jar": "net.minecraftforge:installertools:1.3.1:fat",
     "classpath": ["a:b:1.0", ...],
     "args": ["--task", "MCP_DATA", "--input", "[{MINECRAFT_JAR}]", "--output", "{SIDE}.jar"],
     "outputs": { "{MINECRAFT_JAR}": "client-1.20.1-...jar" },
     "sides": ["client"]
   }
5. 变量替换：{MINECRAFT_JAR} {SIDE} {ROOT} {INSTALLER} + data 表里的客户端映射
6. 为每个 processor 构造完整 classpath（含 installer 内嵌 maven/ 里的 jar），
   用内核 Java 进程执行：java -cp <cp> <processorMainClass> <args...>
7. 逐个执行，检查退出码与 outputs 文件是否生成
8. 写版本 json、把 Forge 的 libraries 加入下载计划
```

**这是整个内核最脆的部分**，要点：
- processor 的 classpath 有些 jar 在 installer 内部（`maven/` 目录），需要先解压到本地 maven 仓库布局再引用。
- 某些 processor 需要 `--offline` 之外的行为差异，要按 `sides` 过滤（`client` / `server`）。
- 全程要把 stdout 写进 launch 日志，出问题时用户能贴日志。
- 建议用"安装脚本可重放"设计：把解析出的 processor 命令序列存成 `install-plan.json`，失败可单独重跑某一步（调试友好）。

**这块一定要有独立的集成测试**：用本地 HTTP 服务托管真实 installer jar 的 fixture，断言最终版本 json 与 expected 一致。否则每次 MC 大版本更新都会坏。

## 6. Java 管理

### 6.1 版本需求表

| MC 版本 | 最低 Java | 推荐 |
|---|---|---|
| ≤ 1.16.5 | 8 | 8（Temurin 8u402） |
| 1.17.x | 16 | 17 |
| 1.18 – 1.20.4 | 17 | 21（1.20.5+ 才必需 21，但 1.20.4 用 21 通常可行且更快） |
| ≥ 1.20.5 | 21 | 21 |

判定依据：优先读版本 json 的 `javaVersion.majorVersion`（官方已声明），**不要自己按版本号猜**。声明缺失（旧版）时才回退到上表。

### 6.2 探测

候选来源（按可靠性排序）：
1. 用户手动指定的路径（实例级覆盖 > 全局）
2. 我们下载管理的 `runtime/java/*`
3. `JAVA_HOME`
4. Windows 注册表 `HKLM\SOFTWARE\JavaSoft\JDK|JRE`、`...\Eclipse Adoptium\JDK`
5. 常见安装路径（`C:\Program Files\Java\*`、`C:\Program Files\Eclipse Adoptium\*`、`/usr/lib/jvm/*`、`/Library/Java/JavaVirtualMachines/*`）
6. `PATH` 上的 `java`

识别版本：`java -XshowSettings:properties -version` 解析 `java.version` / `java.vendor` / `os.arch`。**必须捕获 stderr**（Java 把 version 打到 stderr，这是经典坑）。

结果缓存到 `state/java-cache.json`（路径 + mtime + 版本），避免每次启动都 spawn 一堆 java 进程。

**关键校验**：架构必须匹配（64 位游戏不能用 32 位 Java，ARM64 Windows 上要注意），不匹配要明确提示而不是启动后神秘崩溃。

### 6.3 自动下载

源：Adoptium API（`https://api.adoptium.net/v3/binary/latest/<major>/ga/<os>/<arch>/jdk/hotspot/normal/eclipse`）。可选 Zulu / Microsoft OpenJDK 作为备用。

落地 `runtime/java/temurin-21-x64/`，解压后校验 `bin/java(.exe)` 存在，写 `meta.json`（vendor/major/arch/来源/下载时间）。

## 7. 账户

### 7.1 微软登录（OAuth 2.0 device code flow）

推荐 device code 而非 loopback redirect：
- 不需要在本地起 HTTP 监听（避免端口占用/防火墙弹窗）
- 不需要内置 WebView2 依赖（体积与兼容性）
- 用户体验是"打开链接 + 输入 6 位码"，可接受

流程：

```
1. POST https://login.microsoftonline.com/consumers/oauth2/v2.0/devicecode
   client_id=<Azure 应用 id>  scope=XboxLive.signin offline_access
   → { device_code, user_code, verification_uri, interval, expires_in }
2. 显示 verification_uri + user_code，轮询
3. POST .../oauth2/v2.0/token  grant_type=urn:ietf:params:oauth:grant-type:device_code
   → access_token + refresh_token
4. XBL: POST https://user.auth.xboxlive.com/user/authenticate
   → Token
5. XSTS: POST https://xsts.auth.xboxlive.com/xsts/authorize
   RelyingParty=rp://api.minecraftservices.com/  → XSTS Token + UHS
   错误处理：2148916233 = 无 Xbox 账户；2148916238 = 未成年需家长同意（要给出可读提示！）
6. MC: POST https://api.minecraftservices.com/authentication/login_with_xbox
   → Minecraft access_token（有效期 24h）
7. GET https://api.minecraftservices.com/minecraft/profile
   → { id, name }  （403 = 未拥有游戏）
8. 缓存 refresh_token（加密），MC token 内存+短期缓存
```

实现要求：`client_id` 需要注册 Azure 应用（公开客户端，允许 device code）。**不要**硬编码某个第三方启动器的 client_id。

### 7.2 离线账户

原版离线 UUID 算法（必须一致，否则皮肤/服务器识别出错）：

```
name = 玩家名
hash = MD5("OfflinePlayer:" + name)   // UTF-8
bytes = hash; bytes[6] = (bytes[6] & 0x0f) | 0x30   // version 3
                bytes[8] = (bytes[8] & 0x3f) | 0x80   // RFC 4122 variant
uuid = 标准 hex 格式（带连字符）
```

离线账户的 accessToken 可用任意非空字符串（原版不校验），`userType = "legacy"`。

### 7.3 外置登录（authlib-injector）

这属于 L1 的"账户插件"，但内核要提供支持点：
- 启动时 JVM 参数追加 `-javaagent:<path>/authlib-injector.jar=<apiRoot>`
- 账户记录里带 `apiRoot`，由插件提供

内核只需保证 `LaunchContext.JvmArgs` 可被插件追加 → 这就是为什么外置登录能在不改进内核的前提下实现（M0 的第 2 个验证题）。

## 8. 启动参数构造

### 8.1 顺序

```
[java]
  [-Xmx<n>M -Xms<n>M]
  + arguments.jvm（含 ${natives_directory} ${launcher_name} ${classpath} 等替换）
  + 插件追加的 JVM 参数
  [mainClass]
  + arguments.game（含 ${auth_player_name} ${version_name} ${game_directory} 等替换）
  + 插件追加的游戏参数
```

**`arguments.jvm` 必须包含**（现代版本 json 自带，不要自己加）：
```
-Djava.library.path=${natives_directory}
-Dminecraft.launcher.brand=${launcher_name}
-Dminecraft.launcher.version=${launcher_version}
-cp ${classpath}
```

旧版本没有 `arguments` 字段，用 `minecraftArguments` 字符串 + 手工补 JVM 参数（`-Djava.library.path`、`-cp`）。

### 8.2 占位符表

| 占位符 | 值 |
|---|---|
| `${auth_player_name}` | 玩家名 |
| `${auth_uuid}` | UUID（**无连字符**） |
| `${auth_access_token}` | MC accessToken |
| `${auth_session}` | 格式 `token:<accessToken>:<uuid>`（旧版用） |
| `${user_type}` | `msa` / `legacy` / `mojang` |
| `${version_name}` | 版本 id |
| `${version_type}` | json 里的 type（release/snapshot） |
| `${game_directory}` | 实例 .minecraft 目录 |
| `${assets_root}` | `assets/` 绝对路径 |
| `${assets_index_name}` | assetIndex id |
| `${natives_directory}` | natives 目录 |
| `${launcher_name}` | `ML` |
| `${launcher_version}` | 宿主版本 |
| `${classpath}` | 所有库 + 客户端 jar，`;`（Win）/`:`（*nix）分隔 |
| `${game_assets}` | 旧版 = `assets/virtual/<name>` |
| `${resolution_width}` / `${resolution_height}` | 仅 `has_custom_resolution` 时 |

**引号处理**：路径含空格必须加引号，但不能把 `-cp` 的值包错。做法是**不拼接字符串**，直接构造 `ProcessStartInfo.ArgumentList`（逐参数传，运行时负责转义）。这是避免"用户名带空格就启动失败"的唯一正确做法。

### 8.3 classpath 构造

```
libraries 中所有生效项 → paths
  ├── 跳过 classifier 含 natives- 的（那些不是 classpath 的一部分）
  ├── 跳过 rules 不满足的
  ├── 保留原始顺序（顺序影响 ServiceLoader 行为！）
  └── 末尾追加 versions/<vid>/<vid>.jar
```

**顺序敏感**：Forge 会依赖"自己的 ASM 在官方 ASM 之前"，顺序错会 `NoSuchMethodError`。所以 libraries 合并后的顺序必须稳定且符合官方语义。

## 9. 进程管理

### 9.0 第一件事：控制台输出不是给人看的（真机踩到）

官方 `logging.client.file` 指定的那份 log4j2 配置里，**控制台 appender 用 XML 布局，文件 appender
（`logs/latest.log`）才是文本布局**。所以游戏打给我们的 stdout 长这样：

```xml
  <log4j:Event logger="fuu" timestamp="1792559843620" level="INFO" thread="Render thread">
    <log4j:Message><![CDATA[Created: 256x256x4 minecraft:textures/atlas/chest.png-atlas]]></log4j:Message>
  </log4j:Event>
```

直接塞进日志页就是一片尖括号。`ML.Core/Launch/Log4jXmlFlattener.cs` 把它按**事件**缓冲、压成
`[Render thread/INFO] Created: …`，再交给后续逻辑。

两个必须注意的次序问题：
1. **先压平，再判崩溃特征**。`Exception in thread` / `NoClassDefFoundError` 这些串在 CDATA 里，
   不压平一个都匹配不到——归因会永远落在"未知崩溃"。
2. **进程被杀时 Flush 一次**。最后一个事件可能只写了一半，不 Flush 就会把崩溃现场丢掉。

```csharp
var psi = new ProcessStartInfo(javaPath)
{
    WorkingDirectory = gameDir,
    RedirectStandardOutput = true,
    RedirectStandardError = true,
    RedirectStandardInput = true,          // 支持向控制台发指令（say 等）
    UseShellExecute = false,
    CreateNoWindow = true
};
foreach (var a in args) psi.ArgumentList.Add(a);   // ★ 不用 Arguments 字符串
```

要点：
- **stdout/stderr 分流读取**，用 `ReadLineAsync` 循环 + `Channel<string>` 汇聚，避免 UI 线程被阻塞，也避免缓冲区满了导致游戏卡死（这是最常见的"启动后无响应"原因）。
- **日志双写**：内存尾部 2000 行（给 UI）+ `logs/launch-*.log` 全量。
- **编码**：Windows 控制台输出可能是 GBK（中文系统），必须显式设 `StandardOutputEncoding`，否则中文乱码。
- **进程退出归因**：
  | 退出码 | 含义 | 提示 |
  |---|---|---|
  | 0 | 正常退出 | — |
  | 1 | 一般崩溃 | 展示 crash-report 路径 + 分析 |
  | -1 (0xFFFFFFFF) | 常见于 OOM 或 JVM 启动失败 | 检查内存设置/Java 版本 |
  | 非零且 stderr 有 `OutOfMemoryError` | 内存不足 | 建议降内存或换 64 位 Java |
  | 找不到主类 / `UnsupportedClassVersionError` | Java 版本错 | 指向 Java 设置 |
- **崩溃检测**：退出后扫 `crash-reports/` 最新文件 + 日志尾部 → 匹配规则库（模组冲突、`DuplicateModsFoundException`、`NoClassDefFoundError`、缺失依赖）。规则库设计成可被插件扩展（`ICrashRuleProvider`），这样社区能持续贡献。
- **守护**：游戏运行中宿主退出 → 由设置决定"游戏继续运行"或"一起退出"。Windows 可用 Job Object 绑定，但**默认不绑**（玩家经常关了启动器继续玩）。

## 10. 无头模式（CLI）

Core 无 UI 的直接收益。命令面（M1 只需要前 4 个）：

```
ml versions                          # 列出可用/已安装版本
ml install <mcver> [--loader forge@49.0.30]
ml launch <instance> [--offline-player Steve] [--java <path>] [--memory 4G]
ml status <instance>                 # 是否在运行、最近日志尾部
ml accounts add microsoft            # 走 device code，终端显示码
ml plugins list|install <path>|remove <id>
ml doctor                            # 环境自检：Java、网络、镜像可达性、磁盘空间
```

`ml doctor` 值得单独说：它是**降低支持成本的核心工具**。用户报"启动不了"时，让他跑 `ml doctor > diag.txt`，里面包含环境、Java 列表、镜像连通性、最后的崩溃摘要。这比让用户描述问题有效 10 倍。

## 11. 测试策略（这块决定项目能不能长期活）

| 层级 | 内容 | 手段 |
|---|---|---|
| 单元 | version json 解析、继承合并、rules 求值、classpath 构造、占位符替换、离线 UUID | 纯函数，用真实 json 片段做 fixture。**rules 与 merge 的测试用例要从真实版本 json 抠出来**，不许手写想象的数据 |
| 单元 | 下载引擎状态机 | `HttpMessageHandler` 桩：模拟 404/403/超时/Range 不支持/哈希错 |
| 集成 | 完整安装 → 启动 原版 1.20.4 | 本地静态 HTTP 服务托管精简的 Piston 快照（只留 java 版必需文件），不联网 |
| 集成 | Forge 安装 | 托管真实 installer jar fixture，断言产出 json + processor 调用序列 |
| 集成 | 断网/镜像挂掉降级 | 让本地服务返回 500，断言回退到第二源 |
| 手动清单 | 三平台 × (原版/Forge/Fabric) × (正式版/快照) | 发版前跑一遍 |

**不做**"下载真实几个 GB 再启动游戏"的自动化测试（太慢、太脆）。集成测试用精简 fixture，真机验证放手动清单。
