# 总体方案：插件化 Minecraft 启动器

> 代号暂定 `ML`（Minecraft Launcher）。本文档只定架构与边界，不定实现细节；细节见 `01-插件系统设计.md`、`02-核心启动管线.md`。

---

## 1. 一句话定位

**一个稳定的、可无限扩展的 Minecraft 启动内核。官方只维护"启动这件事"，其余一切——整合包、模组管理、皮肤、服务器、备份、联机、直播——由插件生态承担。**

这跟 PCL / HMCL 不是同一个产品形态：

| | PCL2 | HMCL | 本项目 |
|---|---|---|---|
| 形态 | 全功能单体启动器 | 全功能单体启动器 | 内核 + 插件平台 |
| 扩展方式 | 无（改源码/等作者） | 无（提 PR/等作者） | 官方 API，第三方自由发布 |
| 官方维护范围 | 全部功能 | 全部功能 | 仅内核 + 基础功能 |
| 功能增长 | 取决于开发者投入 | 取决于开发者投入 | 取决于生态 |
| 用户心智 | "一个启动器" | "一个启动器" | "启动器 + 插件市场" |

### 1.1 它们的技术栈（2026-10 实测，来自仓库源码）

| | PCL2 | HMCL | 本项目 |
|---|---|---|---|
| 语言 | **Visual Basic .NET**（2.2 MB）+ C# 辅助（48 KB） | **Java**（7.4 MB） | C# |
| UI | **WPF**（`Application.xaml` / `FormMain.xaml` / `Pages/`） | **JavaFX**（Gradle 自定义插件按平台选 openjfx 分类器） | **WebView2**（HTML + TypeScript） |
| 运行时 | **.NET Framework 4.8**（`<TargetFrameworkVersion>v4.8</TargetFrameworkVersion>`；`PCLCS` 为 `net48`） | **Java 17**（`sourceCompatibility = "17"`） | **.NET 10 LTS** |
| 构建 | msbuild + `windows-latest`，仅 x64 | Gradle Kotlin DSL，3 模块 + 2 个 MC 库子项目 | dotnet CLI |
| 模块划分 | 单工程（Modules/Pages/Controls）+ C# 库 `MeloongCore`（Apache-2.0，2026-04 起外置） | **`HMCL`（UI）/ `HMCLCore`（逻辑）/ `HMCLBoot`（引导）** | Core / Host / Shell / Boot / Cli |
| 跨平台 | Windows only | Win / macOS / Linux（含 deb 打包） | 目标三端 |
| 许可 | 自定义（GitHub 记为 NOASSERTION，条款需单独核） | GPL-3.0 |

源码依据：`Meloong-Git/PCL` 的 `Plain Craft Launcher 2.vbproj`、`PCLCS/PCLCS.csproj`、`.github/workflows/build.yml`；`HMCL-dev/HMCL` 的 `settings.gradle.kts`、`HMCL/build.gradle.kts`、`gradle/libs.versions.toml`。

**三个可直接引用的结论：**

1. **PCL 的栈是我们的反面参照，不是模板。** `.NET Framework 4.8` 意味着没有 `AssemblyLoadContext`（插件隔离的前提）、没有 `PublishSingleFile`、没有现代 GC/JIT；他们要在 net48 上模拟新语法只能用 `PolySharp`——这是被运行时锁住的典型症状。做插件化，这条路走不通。PCL 作者近年把通用逻辑抽成 C# 的 `MeloongCore`，方向也是往分层走，但主程序受 Win7/8 存量用户拖累，换不动。**我们起手 .NET 10 + WebView2，正好是 PCL 想走而走不了的那条路。**
2. **HMCL 已经把 core / ui / boot 三层拆开了**（`HMCLCore` / `HMCL` / `HMCLBoot`），说明"逻辑与 UI 分离"在 MC 启动器上已被验证可行。但它是**编译期模块化，不是运行时插件化**——第三方无法扩展，所有功能仍由上游团队维护。这正是我们的差异化空间。
3. **HMCL 的 `HMCLBoot` 值得直接借鉴。** 引导器解决"运行中的程序不能替换自己的 exe"，而自更新在插件化架构里更进一步：引导器可以在拉起主程序前先做崩溃判定与安全模式决策（见 3.2）。

**关键含义**：我们的竞争对手不是 PCL 的功能表，而是"插件开发者的体验"。API 烂，生态就死，产品退化成第三个 PCL 克隆。所以：

> **插件 API 是本项目的第一个也是最重要的产品，启动器 UI 只是它的第一个消费者。**

## 2. 三个必须先定死的决策

在写第一行业务代码之前，这三件事必须定，否则后面全部返工。

### 决策 A：内核边界（什么进内核，什么永远是插件）

判断标准只有一条：**"从磁盘上已有的东西启动一个实例"所必需的最小闭包**。

> **2026-10-21 修订**：下载**不进内核**。原判据写的是"启动所需的最小闭包"，其中包含
> 下载器；用户明确要求"我们不要下载呀，我们就纯启动器，下载什么靠插件"，于是把边界重画为
> **内核不联网**。这条改动不是文档上改口——`src/ML.Features` 是真实搬出去的代码，
> `tests/ML.Core.Tests/ArchitectureTests.cs` 用程序集引用断言 `ML.Core` 不引用任何 `System.Net*`
> 程序集、也不引用功能层，谁想偷偷加一行 `HttpClient` 都会让构建红。

> **2026-10-22 修订**：**正版登录放宿主层，内核边界不动。**
> 下面「不进内核」里原本写着账户体系走官方插件；但插件系统当前是冻结状态（没有契约、没有加载器），
> 用户要求现在就能用正版账号，于是实现落在 `src/ML.Host/Accounts/MicrosoftAccount.cs`。
> 判据没有被破坏：内核仍然零网络，`LaunchAccount` 只是启动参数里的四个字段，
> 正版与离线走**同一条**启动路径，`ArchitectureTests` 仍然绿。
> 代价是 Host 多了一份**将来应该搬走**的代码——等插件解冻，它应当和 `ML.Features` 一样
> 整体变成官方插件，而不是在 Host 里长成第二层内核。
>
> **2026-10-22 二次修订**：账号从「单条当前身份」改成**账号簿**（正版 + 离线并列，可增删），
> 启动用哪个由实例的 `instance.json → accountId` 决定。这在边界上仍然是同一件事：
> 账号簿只产出 `LaunchAccount`，内核不知道账号从哪来；`accountId` 是可选字段，旧实例照读。

进内核（不可插件化，接口只增不改）：
- 版本元数据解析与继承链展开
- `rules` 求值（当前 OS / 版本 / 架构 / 特性）
- natives 的解压与**架构过滤**（jar 从哪来是插件的事，解压是自己的事）
- classpath 构造、启动参数装配、日志配置引用
- Java 运行时探测与选择（读 `release` 文件与注册表，不联网）
- 进程启动、stdout/stderr 捕获（含 log4j XML 压平）、退出归因
- 实例目录与配置存储
- 插件宿主本身（加载、权限、生命周期）

不进内核（M1 起以"官方内置插件"形式提供，代码和社区插件走同一套 API）：
- **一切下载**：库、客户端 jar、资源对象、Java 运行时、镜像源与降级
- 安装向导的具体 UI 流程
- 账户体系（微软/离线/外置登录）
- 整合包导入、模组管理、皮肤、服务器列表、备份、联机……

推论（重要）：**下载属于插件带来的直接后果是"内核必须对没装好的实例说实话"**。
装不全时内核能做的只有一件事——指出缺哪个文件，然后拒绝启动；起 JVM 只会换来一句
`NoClassDefFoundError`，那会把人的排查方向带偏到"是不是类名写错了"。所以
`ClasspathBuilder` 返回 `MissingFiles`，`LaunchCommand` 带 `MissingClasspathFiles`，
`ShellHost` 见到非空就直接报"请先补齐文件"。这类检查不是测试补丁，是产品能力。

**这条边界是产品的护城河，也是最容易被侵蚀的地方**：一旦遇到"这个功能放核心更省事"，内核就会膨胀回单体启动器。所以内核代码评审的唯一否决标准是：**"这行代码是否只服务于启动的最小闭包？"**

### 决策 B：技术栈

**已定：`.NET 10 LTS` 内核与宿主 + `WebView2` 承载 UI（HTML + TypeScript）+ 三档插件。**

> 这一节在 M0 期间被推翻过一次。原推荐是 `.NET 9 + Avalonia 11`，实机测量和插件 UI 的需求一起把它否掉了。推翻理由保留在下面，因为「为什么改」比「改成什么」更容易被后来的自己误解。

理由：
1. **插件 UI 是代码，不是数据。** 这是决定性的一条。插件要能扩展复杂界面（模组列表、整合包向导、皮肤预览），而 Avalonia 路线下插件只有两个选择：给宿主一棵声明式 POCO 视图树（表达力封顶，复杂交互做不了），或者注入进程内 XAML（插件崩即宿主崩，而且把 Avalonia 整框架冻进插件契约——以后想换 UI 框架等于 API 2.0）。WebView2 是独立渲染进程，插件 UI 崩了宿主还活着，隔离性高一个量级。
2. **MC 启动器的 UI 100% 自定义，框架的原生控件价值用不上。** PCL 和 HMCL 都不使用系统控件：PCL 是自绘 WPF，HMCL 是 JavaFX + 自写 CSS。既然界面本来就是设计出来的，HTML/CSS 在虚拟滚动、3D 皮肤预览、主题换肤、动画、Markdown 渲染上全面强于 XAML，而这些恰好是启动器界面的主要内容。
3. **进程/IO 密集型任务强。** 启动器 80% 的时间在解压、下载、算哈希、拼参数、读写 JSON。`HttpClient` + `System.Text.Json`（源生成）+ `System.IO.Compression` 是这类工作的顶配。
4. **插件隔离有现成机制。** `AssemblyLoadContext`（`isCollectible` 可卸载）是 .NET 独有的成熟进程内插件隔离方案。
5. **体积与启动实测优于 Electron 一个数量级**：自包含单文件 37 MB / 温启 514 ms，对比裸 Electron 运行时 386 MB。**但这不是选 C# 的主要理由**——见下表后两行，AOT 之后体积基本打平。

实测数据（本机，含探针代码）：

| 方案 | 可执行体积 | 启动 | 备注 |
|---|---|---|---|
| Rust 1.94 + Tauri | 4.61 MB（核心探针） | 毫秒级 | 需自写 WebView 桥 |
| C# .NET 10 NativeAOT | 5.63 MB（核心探针） | 19 ms | **不需要 JIT** |
| Go 1.25 + WebView | 5.94 MB（核心探针） | 15 ms | `plugin` 包在 Windows 上运行时报 `not implemented` |
| C# 自包含 JIT + Avalonia | 37.3 MB（R2R）/ 57 MB | 514 ms 温启 | XAML 反射是主要体积/耗时来源 |
| Electron 44 | 386 MB（仅运行时） | 1.5–3 s | 8 周一个主版本，跟不动 |

> **纠正一个容易误判的点**：上表说明「.NET 体积大、启动慢」只对自包含 JIT + XAML 成立，对 NativeAOT 不成立。所以选 C# 的理由是**生态、`AssemblyLoadContext`、以及 WebView2 绑定最成熟**，不是体积。

备选与代价：

| 方案 | 优点 | 代价（为什么不首选） |
|---|---|---|
| Electron + TS | 前端插件最好写，生态最大 | 运行时 386 MB；主进程处理 Java 进程、zip、哈希全要过 Node 层；插件是"任意 JS"，权限模型更难守 |
| Tauri + Rust | 体积与启动最优 | 核心工作量在启动管线（解压/ZIP/JSON/JVM 参数），Rust 写这类代码的工期约为 C# 的 2 倍；插件只能 Rust/WASM |
| Go + WebView | 编译快、二进制小 | Windows 上没有可用的进程内插件机制；WebView 绑定只能 CGO/Wails |
| Avalonia（原推荐） | 单一语言、单一构建、原生控件 | 插件 UI 只能用声明式树或进程内 XAML，见理由 1 |
| Java + JavaFX（HMCL 路线） | 贴近 MC 生态 | HMCL 是 GPL-3.0，代码一行都不能进我们仓库；jlink 打包繁琐 |

> 换语言的架构代价：放弃「官方插件进程内加载」，改成「编译期注册 + 运行时开关」，第三方插件全部进程外 JSON-RPC；声明式 JSON 插件的重要性上升。分层、内核边界、扩展点、权限模型、API 版本策略**全部可以平移**。

### 决策 C：API 稳定性承诺

从 `1.0` 起，插件 API 遵循**语义化版本 + 向后兼容**：
- `1.x` 内只增不改不删；废弃项保留两个 minor 版本，标记 `[Obsolete]` 并在插件管理页提示。
- 破坏性变更只能进 `2.0`，且必须提供 `1.x → 2.0` 迁移指南与兼容垫片（让老插件在新宿主上仍能加载）。
- 内核内部随便重构，**契约程序集 `ML.Plugin.Abstractions` 是唯一冻结面**。

这条承诺的成本是真实的，所以必须在 1.0 之前把 API 压够。做法见决策 A 的推论：**官方功能全部以插件形式实现**，用自己当第一个受虐用户。

## 3. 系统架构

### 3.1 分层

```
┌──────────────────────────────────────────────────────────┐
│  Host（WinForms + WebView2 + Kestrel 静态站点）            │
│  导航 / 主题 / 插件页容器 / 设置页容器 / 通知               │
└───────────────┬──────────────────────────────────────────┘
                │ 只依赖 Abstractions + Host
┌───────────────▼──────────────────────────────────────────┐
│  Plugin Host（插件宿主）                                  │
│  发现 / 版本解析 / 依赖拓扑 / ALC 加载 / 权限门 / 熔断     │
│  扩展点注册表 / 事件总线 / 声明式 UI 渲染器                │
└───────────────┬──────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────┐
│  ML.Plugin.Abstractions  ★ 唯一冻结契约（SemVer 1.x）      │
└───────────────┬──────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────┐
│  Core（无 UI、可无头运行）                                │
│  ┌────────────┬────────────┬──────────┬───────────────┐  │
│  │ Version    │ Download   │ Java     │ Process       │  │
│  │ Resolver   │ Engine     │ Manager  │ Launcher      │  │
│  ├────────────┼────────────┼──────────┼───────────────┤  │
│  │ Instance   │ Storage    │ Diagnostics              │  │
│  └────────────┴────────────┴──────────┴───────────────┘  │
└──────────────────────────────────────────────────────────┘
```

**约束：Core 不允许引用任何 UI 程序集。** 这条约束带来三个好处：无头 CLI 模式免费获得（服务器/CI/自动化可用）、Core 可单测到 90%+、插件可以在无 UI 环境下复用同一批服务。

### 3.2 进程模型

```
ml-boot.exe（引导器，极小、无依赖）
  ├── 判定上次是否非正常退出 → 是否需要安全模式
  ├── 自更新（替换 ml.exe / 内核文件）
  └── 拉起 ↓
      ml.exe (宿主 + Shell)
        ├── 插件 A（in-proc，独立 AssemblyLoadContext）
        ├── 插件 B（in-proc）
        ├── ml.plughost.exe（out-of-proc 沙箱）── 插件 C（不可信/重型/带原生依赖）
        └── javaw.exe（Minecraft 游戏进程，每个实例一个）
```

**为什么需要独立的 `ml-boot`**（借鉴自 HMCL 的 `HMCLBoot`）：运行中的 exe 无法替换自身，自更新必须由一个正在运行的小引导器去做"下载新版本 → 退出主程序 → 覆盖 → 重启"。而插件化让引导器的职责变重了：它还得在拉起主程序**之前**读取 `state/plugin-health.json`，决定是否进入安全模式（禁用全部代码插件）。把这个判定放在引导器而不是主程序里，才能保证"主程序自己因为插件而崩"的情况下仍能救回来。

三档插件形态（详见 `01`）解决一个真实矛盾：**大部分插件要方便，少数插件要安全**。强制全部进程内 = 一个烂插件拖垮整个启动器；强制全部进程外 = 插件作者被 IPC 劝退，生态起不来。

## 4. 功能分级

这是回答"我们做哪些、社区做哪些"的正式表格。**L0/L1 是我们要交付的，L2 是我们要让别人能交付的。**

### L0 — 内核（不可插件化，**零网络**）

| 模块 | 内容 |
|---|---|
| 版本解析 | `version.json` 解析、`inheritsFrom` 链展开、`rules`（os/arch/features）求值、库去重与冲突合并 |
| natives | 从 `version.json` 得出该解压哪些 jar（**按架构过滤**，不是照 rules 全放行）、解压时排除 `META-INF`、清单幂等 |
| 资源布局 | assets 索引里的哈希 → `assets/objects/ab/…` 路径（只算路径，不下载）；旧版 `virtual` / `map_to_resources` 摊平 |
| Java | 注册表 + 环境变量 + `PATH` + 厂商目录 + Mojang 运行时目录五源探测，读 `release` 文件取版本/厂商/位数，按 MC 版本需求选（**不下载 JRE**） |
| 启动 | classpath 构造 + 落盘检查、24 个占位符装配、`logging.client` 引用、起 JVM 进程、stdout/stderr 实时流（log4j XML 压平）、退出码归因与崩溃特征识别 |
| 实例 | 目录布局、每实例配置、并发启动控制 |
| 插件宿主 | 见 `01` |

> **下载（libraries / client jar / assets / JRE / 镜像源与降级）不在这一层**，见 L1 第一行。


### L1 — 基础功能（官方插件，也即 API 的参考实现）

| 功能 | 说明 | 为什么放 L1 而不是内核 |
|---|---|---|
| 下载 | 多源 URL 重定向（Piston 官方 / BMCLAPI / 自定义镜像）、并发池、限速、断点续传、SHA1 校验、失败重试与降级；libraries / client jar / assets / JRE 全在这里 | 设计决策：内核只做「从磁盘上已有的东西启动」，下载靠插件 |
| 版本安装向导 | Vanilla / Forge / NeoForge / Fabric / Quilt / OptiFine 的 UI 流程 | 流程 UI 变化远快于内核，必须能被替换 |
| 账户 | 微软 OAuth（device code）、离线账户、外置登录（authlib-injector） | 认证协议跟着上游变；外置登录必须走插件路径验证扩展点 |
| 实例管理页 | 新建/克隆/删除/重命名、内存与 JVM 参数、版本隔离开关 | 纯 UI + 配置，无内核逻辑 |
| Java 管理页 | 已探测/已下载 JRE 列表、手动指定 | 同上 |
| 日志与崩溃分析 | 实时日志窗、崩溃报告摘要、常见错误归因（内存不足/模组冲突/Java 版本错） | 规则库需要频繁更新，插件化后社区可贡献规则 |
| 设置页 | 下载源、语言、主题、全局内存 | — |

### L2 — 生态（官方不做，只提供 API）

整合包导入/导出（`.mrpack`、CurseForge zip）、模组搜索与更新、模组依赖图、皮肤站、服务器状态与快速加入、存档备份与云同步、联机穿透、录制/直播集成、地图与资源包管理、账号多开与快速切换、启动前置检查（如 Java 补丁、内存优化建议）、Discord Rich Presence……

**其中"整合包导入"我们的建议是：作为首个官方示例插件随启动器可选安装，但不进内核。** 理由：它是插件 API 的最强压力测试——它同时需要下载源扩展、自定义安装任务、进度 UI、实例写入、外部 API 访问；如果这个插件写起来不优雅，说明 API 有问题，此时改还来得及。

## 6. 路线图

| 阶段 | 目标 | 交付物 | 出口标准 |
|---|---|---|---|
| **M0 契约原型**（2–3 周） | 先把 API 想清楚，写 3 个"极端"插件原型 | `Abstractions` 草案 + HelloPlugin + 假想的"整合包导入" + 假想的"外置登录" | 三个原型都能不改内核写完；能列出 10 处 API 不足并修正 |
| **M1 起跑线**（**已达成，真机验收**） | 双击就能用：只启动本机已装好的版本 | Core（Version/Java/Launch/Instance）+ 极简 Shell（版本/实例/日志/设置四页签）+ 打包（便携 exe / 安装包 / 自动更新） | 双击 exe → 选一个已装版本 → 进游戏；缺文件时说清缺哪个而不是抛 NoClassDefFoundError；打包与更新到家 0.1.0 → 0.1.1 → 0.1.2 全程真机跑通 |
| **M2 模组加载器**（3–4 周） | Forge / NeoForge / Fabric 可装可启 | `ForgeInstaller`（含 processors 执行）、`FabricInstaller` | 三类加载器各装一个版本并进入游戏 |
| **M3 插件系统落地**（4 周） | 插件宿主完整 + 官方功能全部插件化 | Plugin.Host、权限、熔断、声明式 UI 渲染器、out-of-proc | 卸载全部官方插件后宿主仍能启动并显示"无功能"空态 |
| **M4 对外 1.0**（3 周） | 可发布 | 发布包、插件开发文档、`dotnet new ml-plugin` 模板、社区索引雏形 | 外部开发者不看源码、只读文档能写出可用插件 |
| **M5 生态** | 插件市场、签名、评分、自动更新 | 索引服务 + 客户端市场页 | — |

M0 是**不可跳过**的。跳过它的项目，100% 会在 M3 遇到"插件需要访问内核内部"的塌方。

## 7. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| **API 设计不足，插件要 hack 内部** | 生态畸形，只能靠反射和改源码 | 官方功能全部插件化（无后门）；`plugins/` 禁止访问 `ML.Core.*`；M0 契约原型先行 |
| **API 过度设计，插件作者被劝退** | 没人写插件，产品退化为第三个 PCL | UI 双轨（声明式 DSL 为主，XAML 为辅）；`dotnet new` 模板；HelloPlugin 控制在 20 行内 |
| **插件是任意代码执行** | 恶意插件偷 accessToken、删档 | 权限清单 + 首次安装确认 + 敏感数据（token）默认不对插件可见；进程外沙箱选项；签名与来源标记 |
| **插件互相冲突** | 用户排查困难，口碑崩 | 显式 `loadAfter`/`loadBefore`、依赖拓扑、冲突声明；提供"安全模式"（禁用全部非必要插件启动一次） |
| **一个烂插件拖垮宿主** | 用户认为"启动器不稳定" | 插件异常全包裹 + 连续失败熔断禁用 + 崩溃时记录插件栈并提示"由 X 插件引起" |
| **内核膨胀回单体** | 差异化消失 | 代码评审唯一否决标准：是否只服务启动最小闭包；**内核零网络**由 `ArchitectureTests` 断言程序集引用，不靠自觉 |
| **分发合规** | 下架/法务风险 | 只做"从官方或镜像下载"，绝不打包分发 Mojang 资源；不内置盗版源；微软登录只走官方 OAuth 端点 |
| **长期兼容成本** | 1.x 承诺被违约 | 契约程序集极小化；扩展点以"能力注册"为主而非"抽象基类继承"，减少改动面 |

## 8. 关键决策

| 项 | 结论 |
|---|---|
| 技术栈 | `.NET 10 LTS + WebView2`（见决策 B） |
| 平台范围 | 只做 Windows。路径处理写成可移植的，但不为其他平台做适配与验证 |
| 插件分发第一步 | 本地 zip 安装 + 手动更新；社区索引服务留到后面 |
