# 03 · 插件能力盘点与缺口清单

> 盘点日期：2026-10-24
> 依据：`src/ML.Plugin.Abstractions/IPlugin.cs`、`PluginPermissions`、`PluginManifest`、`src/ML.Web/app.js` 的实际实现
> 用途：回答"别人能做出什么样的插件"，以及"要做到某些类型还差什么"

---

## 0. 一句话结论

**插件本质是「往 WebView2 页面里注入 HTML/JS」+「通过契约调用宿主动作」。**

推论：

- **纯页面层能表达的东西，基本都能做**（界面、动画、小游戏、iframe、编辑器 UI）
- **想插手宿主流程**（否决启动、替换宿主页面、改设置）→ 做不了
- **想碰进程/系统**（执行代码、起服务器）→ 契约没给，只能自己 `Process.Start` 硬来

注意：契约是**推荐路径，不是安全边界**。插件同进程、是普通 .NET 程序集，反射和 BCL 都能用。

---

## 1. 现在能做什么

### 1.1 生命周期

| 能力 | 接口 | 约束 |
|---|---|---|
| 初始化 | `IPlugin.InitializeAsync(ctx, ct)` | 10 秒超时，超时当该插件失败 |
| 卸载 | `IPlugin.ShutdownAsync(ct)` | 3 秒超时，之后强制 `Unload()` + 主动 GC |
| 启动前改参数 | `ILaunchHook.OnBeforeLaunch(req)` | **只能追加，不能否决**（返回 `void`） |
| 监听事件 | `IEventHook.OnHostEvent(name, json)` | 3 个事件，纯通知 |
| 响应界面调用 | `IPluginCommand.ExecuteAsync(cmd, payload, ct)` | 插件页面调自己 C# 的通道 |
| 键值设置 | `IPluginSettings.Get/Set/All` | `plugin-data/<id>/settings.json` |
| 写日志 | `IPluginLogger.Info/Warn/Error` | 宿主统一加前缀落盘 |

### 1.2 能读的状态

| 能力 | 成员 | 内容 |
|---|---|---|
| 游戏根目录 | `Host.GameRoot` | `.minecraft` 路径 |
| 实例列表 | `Host.Instances` | Name / VersionId / Directory / GameDirectory / ModsDirectory / AccountName |
| 已装版本 | `Host.Versions` | 只有 `Id` + `Type` |
| 当前账号 | `Host.CurrentAccount` | Name / Kind / Uuid，**没有令牌** |
| 插件目录 | `ctx.Directory` | 只读，覆盖升级会清 |
| 可写目录 | `ctx.DataDirectory` | `plugin-data/<id>/`，升级不丢 |

### 1.3 能做的动作

| 能力 | 成员 |
|---|---|
| 启动实例 | `Host.LaunchAsync(name, ct)`，失败返回原因不抛 |
| 查 Mojang 版本清单 | `Installer.ListRemoteAsync(includeSnapshots, ct)` |
| 装版本 | `Installer.InstallAsync(versionId, progress, ct)`，走下载队列 |
| 提交下载任务 | `Downloads.Submit(title, files)` |
| 等下载完成 | `Downloads.WaitAsync(id, ct)` |
| 查下载状态 | `Downloads.Status(id)` |

### 1.4 界面（4 个插槽）

| 插槽 | 位置 | 需要 `ui:page` |
|---|---|---|
| `page` | 侧栏一整页 | 是 |
| `settings` | 设置弹窗里的一块 | 否 |
| `instances.toolbar` | 实例页工具栏 | 否 |
| `account.before-list` | 账号列表上方 | 否 |

插槽里的脚本用 `new Function('MLPlugin', script)` 执行，**同上下文**，`document` / `window` 直接用。

### 1.5 权限

| 权限 | 状态 | 拦住什么 |
|---|---|---|
| `launch:jvm-args` | 强制 | 往 JVM 参数里加东西（含 `-javaagent`） |
| `launch:game-args` | 强制 | 往游戏参数里加东西 |
| `ui:page` | 强制 | 挂界面片段 |
| `network:https` | 预留，不生效 | — |
| `fs:instance` | 预留，不生效 | — |
| `account:token` | 预留，不生效 | — |

强制权限需要**插件声明 + 用户同意**两步，缺一步就拒绝（审计日志记 `denied` / `consent-required`）。

## 2. 做不到什么

| 做不到 | 原因 |
|---|---|
| 否决一次启动 | `OnBeforeLaunch` 返回 `void` |
| 拦截任意宿主操作（waterfall） | 没有这种钩子 |
| 改宿主设置 | `settings.update` 不在契约里 |
| 停用/启用别的插件 | 没有这个 API |
| 定义权限规则 | 判断逻辑写死在宿主 |
| 做审批流 | 只有一次静态的权限同意 |
| 拿到账号令牌 | `CurrentAccount` 只给 Uuid |
| 让子进程在启动器死后继续活 | 刻意不做：插件起的进程一律随启动器退出（含崩溃） |
| 读游戏 stdout | 宿主自己接日志，没暴露给插件 |
| 替换宿主页面 | 只能加 `page`，不能覆盖 `panel-home` / `panel-instances` |
| 启动阶段钩子 | 没有"启动器正在启动"的事件 |

## 3. 典型插件评估

### 3.1 四类主流插件

| 类型 | 结论 | 卡点 |
|---|---|---|
| **联机插件** | ✅ 约 85% 能行 | 缺 `HostInstance.Running`（是否在跑）、`HostVersion.Number`（游戏版本号，匹配协议） |
| **开服插件** | 🟡 能做但费劲 | 宿主没有"服务器实例"概念，也没有进程管理；控制台、日志、停止全要插件自己造 |
| **美化插件** | ✅ 约 70% 能行 | 靠注入全局 CSS 覆盖宿主变量，没有正式皮肤 API，宿主改版就断 |
| **大改造插件** | 🟡 只能改一半 | 能加自己的页，不能替换宿主页面/启动流程/设置项 |

### 3.2 五类"花活"

| 想要 | 结论 | 说明 |
|---|---|---|
| **启动器启动动画** | 🟡 能凑合，但会闪 | 能注入全屏遮罩，但插件页面在首屏之后挂载，主界面会先闪一下；缺 `startup` 插槽 |
| **启动器启动密码** | 🟡 同上 | 逻辑能写（插件自己存哈希、自己校验），问题同样在时机；忘了密码可以用崩溃恢复的"关闭所有插件并重启"兜底 |
| **内置小游戏** | ✅ 能 | 纯前端，`page` 插槽 + Canvas |
| **内置网页版 MC** | ✅ 能 | `<iframe>` 或 canvas+wasm；法律风险自负 |
| **内置编程（IDE）** | 🟡 一半 | 编辑器（Monaco/CodeMirror）能加载；**代码执行做不了**（没有进程管理，`Process.Start` 硬来没有输出捕获、没有停止、没有超时） |

## 4. 缺口清单（按投入产出排序）

| # | 缺什么 | 改动量 | 解锁 |
|---|---|---|---|
| 1 | `HostInstance.Running`（已加）、`HostVersion.Protocol`（已加但本地读不到，见下） | 极小 | 联机插件能判断"该连哪个实例" |
| 2 | `startup` 插槽 | 小 | 启动动画 + 启动密码做到无缝（不用 `page` 硬凑） |
| 3 | `OnBeforeLaunch` 可否决（`HookResult`） | 小 | 游戏启动前的“密码/检查/拦截”类插件 |
| 4 | `launch.preparing` 事件（点了启动、正在准备） | 很小 | 启动动画的正确触发时机 |
| 5 | 主题变量文档化 + 固定语义 | 小 | 美化插件不用靠猜 class 名 |
| 6 | ~~受控子进程~~ **已做（最小版）**：`Host.AdoptProcess(pid)` 绑 Job Object，进程树随启动器死；起/收/发/停由插件用 BCL 自己做 | 小 | 开服、内置编程 |

1~5 加起来是一天内的量，6 是独立子系统，要单独设计。

**关于协议号**：`HostVersion.Protocol` 字段加了，但**目前恒为 null** ——
实测 1.21.8 的 `version.json` 里没有 `protocolVersion`，协议号只在 ping 服务器时才有。
联机插件现在要用，得自己维护"版本 → 协议号"的映射表。

## 5. 与 DSH 的定位差别

| 维度 | DSH | 我们 |
|---|---|---|
| 模型 | 可编排权限 + 硬底线 | 全信任插件，只做能力门 |
| 插件能否改权限规则 | 能 | 不能 |
| 能否拦截操作 | 能（waterfall） | 不能（只有事后通知） |
| 沙箱 | 有，可插拔 | 没有，同进程 |
| 审批流 | `ctx.approval` | 只有一次静态同意 |
| 红线 | `ctx.tools.guard()` | 没有 |
| 崩溃 | 推测隔离 | 不隔离，但有崩溃恢复（四按钮） |
| 停用插件 | — | 3 秒后强制卸载，插件拦不住 |

**取向不同，不是水平不同。**

我们跑在"操作游戏目录"的场景，最坏情况是存档没了；DSH 跑在"操作文件系统 + 执行 shell"的场景，插件来自社区且不可信。它需要权限体系是刚需，我们需要的是**给够能力 + 坏了好恢复**。

## 6. 结论

插件生态现在的瓶颈**不是权限，是缺几个平台级能力**：

1. 两个字段（运行状态、游戏版本号）—— 几十行
2. `startup` 插槽 —— 半天
3. 可否决的启动钩子 —— 半天
4. 外部进程管理 —— 一个子系统

前三个做完，"启动动画 / 启动密码 / 联机 / 美化"这几类就能正经做出来。

第 6 项已经落地成最小形态：宿主不包装进程管理（那是标准 BCL 的事），只提供
`AdoptProcess(pid)` 把子进程绑进 Job Object —— 启动器一退，整个进程树跟着消失。
实测：起一个 ping、强杀启动器，2.5 秒后该进程已不存在。

**一个例外：P2P 打洞不需要第 6 项。** 插件自己用 `UdpClient` 打洞、用 `HttpClient` 连信令服务器、
用 `AddGameArgument("--server", ...)` 让游戏连上——这些现在都有，纯插件内就能做完。
只有"套现成隧道工具（frp / n2n 的 exe）"才需要子进程。

**子进程的定位（2026-10-24 定）**：随启动器退出一起结束，不做常驻、不做后台服务。
启动器是壳，插件是壳的延伸——关掉壳，壳里出来的东西也该没了。
