# 性能基线

所有数字都是**本机实测**，不是估算。硬件/网络变了就重跑，重跑方式见每节末尾。

跑法：

```powershell
dotnet run --project tools/ML.Verify -c Release -- java 17
dotnet run --project tools/ML.Verify -c Release -- version tests/fixtures/vanilla-1.20.1.json D:\tmp\mc
dotnet run --project tools/ML.Verify -c Release -- assets D:\tmp\mc 400 D:\tmp\mc\assets\indexes\5.json
```

`ML_CONCURRENCY` 环境变量控制并发，默认 8。

---

## 1. 下载引擎：真实 CDN，1.20.1 的 66 个文件

任务集 = 88 个库里 Windows 放行的全部 + `client.jar` + 资源索引，净 84,317,997 字节（80.4 MB）。

| 并发 | 用时 | 吞吐 | 失败 |
|---|---|---|---|
| 8 | 40,163 ms | 2.0 MB/s | 0 |
| 16 | 94,119 ms | 0.9 MB/s | 0 |
| 32 | 44,711 ms | 1.8 MB/s | 0 |

**结论：并发从 8 加到 32 没有任何收益，吞吐在 0.9–2.2 MB/s 之间随机波动。瓶颈是这条线路到 Mojang CDN 的带宽，不是我们的引擎。**

这条结论直接决定了两件事：

1. 默认并发就是 8。往上升只会让日志更乱、失败重试更贵。
2. **镜像源比线程数重要一个数量级。** 换成国内镜像能省的是分钟级时间，加线程省的是零。所以下载器必须把「URL 怎么来」做成可替换的接缝，让镜像插件能挂上去——这属于内核必须提供的**能力**，尽管「管哪些镜像」是插件的事。

---

## 2. 已装好的校验成本（每次启动都要付）

第二轮跑同一批任务，全部命中 `AlreadyValid`，一个请求都不发。

| 任务集 | 文件数 | 用时 | 速率 |
|---|---|---|---|
| version（库 + client.jar + 索引） | 66 | 79 ms | 约 840 文件/秒 |
| assets 抽样 | 400 | 74 ms | **5,397 文件/秒** |

差异来自文件大小：库文件平均 1.2 MB，抽样资源平均 322 KB。SHA1 走流式计算，84 MB 在 79 ms 内算完，说明哈希不是瓶颈。

**推算完整 1.20.1（约 4,100 个文件 / 约 400 MB）：校验约 0.8–1.0 秒。** 这是启动器每次启动的固定成本，可以接受，不需要做「跳过校验」的优化开关。

## 6. Java 探测耗时（每次启动都要付）

五个来源全扫（用户指定 / `JAVA_HOME` / `PATH` / 注册表 / 厂商目录 / Mojang 运行时），本机 4 个安装：

| 指标 | 数值 |
|---|---|
| 全量扫描 | **27 ms** |
| 单个安装检查（读 `release`） | 亚毫秒级 |
| 单个安装检查（`release` 缺失，退化成跑 `java -version`） | 约 100–300 ms |

不启动 JVM 就能判定的绝不启动——`release` 文件里已经有版本、厂商、位数，跑进程只是为了兜住 Java 8 的 JRE 版这种没有 `release` 的老布局。

**这条性能预算说明**：Java 扫描可以直接放在每次启动的关键路径上，不需要缓存到磁盘（缓存反而会带来「用户卸了 Java 但缓存还说有」的报错）。

## 7. natives 解压与架构过滤（真实 1.20.1）

`ml-verify natives <目录> tests/fixtures/vanilla-1.20.1.json` 的实测输出。

**先看正确性，这才是这段代码存在的理由。** 1.20.1 里每条 LWJGL 库都有三个 Windows 变体（`natives-windows` / `-x86` / `-arm64`），而它们的 `rules` **只判断 `os.name == windows`，不判断架构**。所以规则层面放行 `7 × 3 = 21` 个 jar，其中只有 7 个属于 64 位机器：

```
选中 7 个 jar，按架构跳过 14 个
  跳过（架构不符）org.lwjgl:lwjgl:3.3.1:natives-windows-arm64
  跳过（架构不符）org.lwjgl:lwjgl:3.3.1:natives-windows-x86
  …
```

如果照 rules 无脑解压，`lwjgl.dll` 会被 x86 或 arm64 版本覆盖，游戏启动时拿到的是错位数的 dll——表现是 `UnsatisfiedLinkError`，或者干脆进程直接退出。这条**必须靠架构过滤解决，rules 帮不上忙**。

| 指标 | 数值 |
|---|---|
| 选中 jar | 7（约 1,467 KB） |
| 按架构跳过 jar | 14 |
| 首次解压 | **39 ms**，写入 18 个文件，共 3,355,159 B |
| 二次解压（清单命中） | **4 ms**，写入 0，跳过 18 |
| 冲突 | 0 |

18 个文件是 7 个 dll（`lwjgl.dll` 457 KB、`lwjgl_stb.dll` 506 KB、`lwjgl_opengl.dll` 362 KB、`glfw.dll` 366 KB、`jemalloc.dll` 282 KB、`lwjgl_tinyfd.dll` 249 KB、`OpenAL.dll` 1,131 KB）加上 LWJGL 自带的 `.sha1` / `.git` 校验文件——后者要留着，LWJGL 自己的库加载器会读。

**结论**：natives 解压耗时在几十毫秒量级，**不构成启动瓶颈，不需要任何优化或缓存**；清单文件的作用不是性能，而是让「jar 集合没变就不重复解压」这个语义成立。真正的价值在那 14 个被拦掉的 jar 上——这是正确性，不是速度。

（旧版 `virtual` / `map_to_resources` 布局的摊平只有单测覆盖，没做真机网络验收：要完整验一次得装 1.6.4，价值不大。这条如实记在这里，不当成已验证。）

## 8. 端到端：从空目录到游戏窗口（vanilla 1.20.1）

全链路一次跑通，机器与线路同前。命令：`ml-verify launch <空目录> tests/fixtures/vanilla-1.20.1.json 40`。

| 阶段 | 数据 |
|---|---|
| 库 + client.jar | 67 项 / 80.4 MB（其中 client.jar 23.0 MB） |
| natives | 选中 7 个 jar、按架构跳过 14 个 / 1,467 KB / 解压 39 ms |
| 资源对象 | 任务 3,598 个 → 按哈希去重后 3,575 个文件 / 621.3 MB（23 条是同哈希不同名） |
| Java | 17.0.17（注册表来源），`SelectBest` 精确命中 |
| classpath | 44 项，**缺失文件 0** |
| 参数装配 | 未解析占位符 **0**，可选参数（`--width/--height` 之外的 quickPlay 系列）整条丢弃 |
| 游戏启动 | 观察 40 秒后主动杀，`TimedOut`，见到初始化特征 |

游戏侧的真确证（从 stdout 里抓的实况）：

```
Setting user: Dev
Backend library: LWJGL version 3.3.1 build 7
OpenAL initialized on device OpenAL Soft on 扬声器 (HECATE G2 GAMING HEADSET)
Sound engine started
Created: 256x256x0 minecraft:textures/atlas/paintings.png-atlas
```

**「能启动」这条验收线的价值**：它一次性证明了解析、继承合并、rules 求值、下载与 SHA1 校验、natives 架构过滤、assets 落盘、Java 选择、24 个占位符装配、进程管理九件事同时正确。任何一环错了，这里起不来。

### 这一轮真机上抓到的两个"看不出病因"的错

两个 bug 的报错信息都指向别处，值得记下来：

1. **`ClassNotFoundException: net.minecraft.client.main.Main`** —— 看起来像"游戏没装"，实际是 client.jar 落盘名是 `client.jar` 而 classpath 按 `versions/<id>/<id>.jar` 找。**统一按 `GamePaths.ClientJar(id)` 落盘**即可。
2. **`NoClassDefFoundError: joptsimple/OptionSpec`** —— 看起来像"库缺失/损坏"，实际是下载落盘少了 `libraries/` 一层前缀：文件下到了 `<根>/net/sf/…`，而 classpath 指向 `<根>/libraries/net/sf/…`。**所有库路径必须由 `GamePaths.LibraryFile` 单点生成**。

为此给 `ClasspathBuilder` 加了落盘检查：`ClasspathPlan.MissingFiles` 列出 classpath 里不存在的文件，`LaunchCommand.MissingClasspathFiles` 透传给调用方。**起 JVM 之前就能拦住，不用等 Java 用一行 NoClassDefFoundError 猜谜。**

（复用性结论：凡是让人"往错误方向排查"的报错，都值得在内核里加一道显式检查，把它变成一句能读懂的话。）

## 9. 分发体积与冷启动（打包实测）

| 形态 | 体积 | 冷启动到首屏 |
|---|---|---|
| 单文件 `Enderman Launcher.exe`（self-contained 单文件，页面内嵌） | **61.3 MB** | **3.1–3.2 s** |
| 便携版 zip（同上一个 exe 压缩） | 56.1 MB | — |
| Velopack 安装包 `Setup.exe` | 65.8 MB | — |
| 差分更新包（0.1.1 → 0.1.2） | **117 KB** | — |

对照（本机实测，见 ADR 0001）：Electron 44 **仅运行时** 386 MB、首屏 1.5–3 s；Avalonia 11 修剪 + R2R 37.3 MB、温启 514 ms。

三点值得记的：

1. **页面必须编进程序集**。早先 Kestrel 从 `src/ML.Web` 磁盘目录服文件，只能在仓库里跑；打成单文件后那个目录不存在，双击就是白屏。改成嵌入资源后 exe 完全自包含，另留 `ML_WEB_DIR` 环境变量做开发覆盖。
2. **差分更新非常划算**。单文件 exe 每次改动都整体变大，但因为压缩后的可执行段高度相似，117 KB 的 delta 就能从 0.1.1 升到 0.1.2——这条直接决定「用户愿不愿意点更新」。
3. **冷启动 3.1 s 不是我们的代码慢**：其中绝大部分是 WebView2 运行时初始化 + 本地 Kestrel 起监听。Rust/Go/C++ 方案在这两项上省不下来（同样要 WebView），所以不值得为启动速度换语言。
