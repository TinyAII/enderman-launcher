# ADR 0001 — 技术栈：.NET 10 + WebView2 + 三档插件

- 状态：**已接受**（2026-10-20）
- 决策者：项目所有者
- 取代：`docs/00-总体方案.md` 早期章节中的「.NET 9 + Avalonia 11」推荐

## 背景

我们要做一个**插件化的 Minecraft 启动器**：官方只做「启动一个实例的最小闭包」，其余全部由插件承担，官方不审不维护插件。这与 PCL2 和 HMCL 的定位不同。

技术栈必须满足六条硬要求：

1. 能优雅地管住**进程外进程**（Java、插件进程），包括崩溃回收、残留清理。
2. 隐藏文件下载 + 并发下载 + 解压 + 哈希校验要能用成熟库，不能自己造。
3. 插件界面要能承载**复杂 UI**，而不是只有表单和列表。
4. 插件崩溃不能带崩宿主。
5. 安装包和冷启动不能让用户觉得笨重。
6. 团队规模小，长期维护成本必须低。

## 决策

| 层 | 选型 |
|---|---|
| 内核 / 宿主 | **.NET 10（LTS）** |
| UI 容器 | **WebView2**（Windows 用系统已装的 Edge WebView2 Runtime） |
| UI 实现 | **HTML + TypeScript + Vite** |
| 插件形态 | 三档：① 声明式 JSON ② 官方内核插件（C#，`AssemblyLoadContext` 可卸载）③ 社区插件（任意语言，独立进程 + JSON-RPC over stdio） |
| 界面扩展方式 | 插件提供 **HTML/TS 资源包**，在 WebView 的独立渲染进程里跑 |

## 备选方案与实测数据

测试方法：同一套「启动管线骨架」功能（HTTP GET + JSON 解析 + ZIP 打开 + SHA1 + MD5 + 起子进程 + 并发），各语言实编译测；体积为最终可分发产物，启动为纯进程启动耗时。

| 方案 | 可执行体积 | 纯启动 | 构建耗时 | 结论 |
|---|---|---|---|---|
| 裸 Electron 44.7.0 运行时 | **386 MB / 79 文件** | 1.5–3 s | — | 否决：跟不动 8 周一个主版本 |
| C# 自包含 JIT + Avalonia 11（修剪+R2R） | 37.3 MB | 514 ms（温启） | 16 s | 体积/启动可接受，UI 表达力不足 |
| C# .NET NativeAOT | 5.63 MB | **19 ms** | 15.6 s | AOT 后与 Go/Rust 完全打平 |
| Go 1.25 + WebView | 5.94 MB | 15 ms | 3.9 s | 备选：插件模型弱 |
| Rust 1.94 + Tauri | 4.61 MB | 同量级 | 26 s | 备选：核心逻辑工期约 2× |
| C++ + Qt QML | 16.9 KB（仅 STL） | — | <1 s | 否决：HTTP/JSON/ZIP/crypto 全要自造 |

三条否决理由：

- **Electron**：纯运行时基线 386 MB。DSH 那种应用可以接受，一个启动器不行。
- **Avalonia**：Minecraft 启动器的 UI 是 100% 自定义的（PCL/HMCL 都没用系统控件），Avalonia 的核心价值——原生控件 + MVVM 强类型——正好用不上。而虚拟滚动、皮肤 3D 预览、主题、动画、Markdown 渲染这些**真需求**上，Web 方案全面领先。
- **C++**：体积优势只在「仅 STL」时成立。一旦加上 HTTP/JSON/ZIP/哈希，工程量和依赖管理成本就失控，相对工期约 2.5–3×。

## 决定性理由：插件 UI

前两条都只是「哪个更好」，真正的分水岭是插件如何扩展界面。

DSH（DeepSeek Harness）的做法——客户端插件就是真 JS 模块，宿主把模块清单扫成 `window.__DSH_BOOT__`——证明了一件事：**插件的 UI 是代码，不是数据**。

如果宿主 UI 是 Avalonia，插件只剩两条路：

1. 声明式 POCO 视图树，宿主渲染 —— 表达力天花板很低，稍微复杂一点就撞墙。
2. 进程内加载 XAML —— 插件崩了宿主就崩，而且等于把整个 Avalonia 冻进 API 契约，永远不能升级。

WebView2 是**独立渲染进程**：插件 UI 崩溃只影响它自己的渲染进程，宿主毫发无伤。这比进程内 XAML 安全一个量级，而且插件用的是浏览器那套成熟模型，不用学任何私有视图 DSL。

这一条把 Avalonia 直接否掉了。

## 实测验证（Walking Skeleton）

四条集成边界已在真机上跑通并发结论落盘（`artifacts/skeleton-metrics.json`）：

| 边界 | 结果 |
|---|---|
| ① .NET 10 + Kestrel 本地服务 | 通，`http://127.0.0.1:<随机端口>` |
| ② WebView2 加载页面 | 通，渲染器为 `Edg/143.0.0.0`（Chrome/143） |
| ③ JS ↔ .NET 桥往返 | **中位 0.3 ms**，p95 47.9 ms（20 次采样，1 次离群） |
| ④ 进程外 Node 插件握手 | 通，pid 正常，握手 **0.053 ms** |

桥的 0.3 ms 中位意味着：不需要为「高频小消息」做特殊优化，只要按 60 Hz 批量推送进度即可。p95 出现一次 47.9 ms 离群，来源待查（可能是首帧路由预热），不影响结论。

## 后果

**好的：**

- 内核与 UI 彻底解耦：内核是零 UI 依赖的类库，UI 是纯 Web 资源，两边可以各自演进。
- 插件 UI 崩溃隔离；插件 UI 作者用他本来就会的 HTML/CSS/JS。
- 分发体积可控：自包含发布 + 修剪后 30–40 MB 量级，AOT 路径还能再压到个位数 MB。
- 进程外插件对语言完全中立，社区用 Python/Go/Rust/JS 写都行。

**代价：**

- **双语言双构建**：C# 一份、TS 一份，CI 要跑两条链。
- **WebView2 只有 Windows**。跨平台需要换 WKWebView（macOS）/ WebKitGTK（Linux），届时 UI 代码不用改，但宿主那层窗口容器要重写。
- .NET ↔ JS 之间传大对象要序列化。骨架证明小消息便宜，但**大列表（十万条版本文件）需要走分页或二进制通道**，这一点尚未实测。
- `AssemblyLoadContext` 的可卸载性有已知陷阱（静态字段、事件订阅、线程会阻止卸载），官方插件必须遵守卸载纪律，否则会泄漏。

## 边界约定

- 本 ADR 只决定 M0–M1 的栈。如果将来 WebView2 的桥性能或跨平台要求推翻结论，走 ADR 0002，不直接在代码里分叉。
- `ML.Plugin.Abstractions` 是唯一冻结面，只能引用 `System.*`；不得把任何 UI 框架类型放进契约。
