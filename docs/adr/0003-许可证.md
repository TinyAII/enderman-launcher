# ADR 0003：GPL-3.0 + 插件例外

- 状态：已定（2026-10-21）
- 相关：[LICENSE](../LICENSE)、[LICENSE-EXCEPTION](../LICENSE-EXCEPTION)、[LICENSE-APACHE-2.0.txt](../LICENSE-APACHE-2.0.txt)

---

## 决策

| 范围 | 许可 |
|---|---|
| 本仓库全部内容（宿主 `src/ML.Host`、内核 `src/ML.Core`、界面资源） | **GPL-3.0-or-later** |
| 第三方插件 | **任意许可**（含专有），由插件作者自定 |
| 契约程序集 `src/ML.Plugin.Abstractions` | **Apache-2.0**（单独授权，见 `LICENSE-APACHE-2.0.txt`） |

`LICENSE-EXCEPTION` 是依据 GPL-3.0 第 7 条（Additional Permissions）写的插件例外，三条实质内容：

1. 插件可任选许可，不因被本程序加载/调用而变成 GPL 衍生作品。
2. 例外只覆盖**未修改的**本程序；改了本体再分发，整个修改版仍须 GPL-3.0。
3. 把本程序与插件打成一个整体分发物（同一安装包），该整体仍须 GPL-3.0。

---

## 为什么不是 MIT（DSH 的选择）

DSH 用 MIT 是合理的：它是**平台型**项目，要的是最大扩散。我们的处境不同——我们要的是「**不被闭源 fork 拿去改成收费启动器**」，并且我希望这个项目长期由社区共同维护而不是被某个商业壳吞掉。GPL-3.0 是唯一既能保证这一点、又不至于把用户挡在门外的选择（PCL2 是自定义许可、HMCL 是 GPL-3.0，玩家对 GPL 启动器没有心理门槛）。

## 为什么不是 AGPL-3.0

AGPL 的第 13 条针对「通过网络提供服务」。启动器是**本地程序**，不提供服务端；加 AGPL 只增加理解成本与法务疑虑，没有任何实际收益。

## 为什么必须写插件例外

不写的话，`AssemblyLoadContext` 把插件程序集加载进宿主进程、并直接引用宿主的 `ML.Core` 类型，在多数法律意见下构成**衍生作品**——于是所有插件都被迫 GPL-3.0。这会把「插件千变万化」这件事从根上掐死：整合包作者、服主、想靠插件做增值的人全部退场。

标准解法就是 GPL-3.0 第 7 条的额外许可（GCC 的 runtime library exception、Autoconf 的 exception 都是这个模式）。另外把契约程序集单独以 Apache-2.0 授权，让插件作者**一行 GPL 代码都不用碰**就能编译。

---

## 后果与要求

1. 仓库根必须有 `LICENSE`（GPL-3.0 全文）、`LICENSE-EXCEPTION`、`LICENSE-APACHE-2.0.txt` 三个文件，发包时一并带上（安装包内也要有）。
2. **每个源文件不必单独写版权头**（GPL-3.0 允许集中声明），但 `README` 必须显式声明许可与例外，否则使用者无从得知额外许可存在。
3. 一旦引入第三方 GPL 不兼容代码（例如 GPL-2.0-only 的库），整个仓库即无法再分发——引入新依赖时要看许可证，这一条比技术选型更容易出事。
4. `src/ML.Plugin.Abstractions` 将来若独立成仓库，`LICENSE-APACHE-2.0.txt` 随包走，本仓库保留一份以便阅读。
5. 插件例外是**授予第三方**的，不是授予我们自己的；我们自己发布的官方插件同样受 GPL-3.0 约束（因为我们同时是宿主作者，分不清「独立作品」）。
